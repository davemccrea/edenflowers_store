# Unqueried booleans over the Balance are computed in Elixir

Calculations are Ash expressions by default. One definition then works in a filter, a sort, an aggregate and a load, and reads in the same language as its neighbours.

The exception is a calculation that builds on the Balance chain (`balance`, `payment_status`, `settled?`, `payable?`, an invoice's status) when nothing filters, sorts or aggregates on it. That one is computed in Elixir: an inline function in the resource, with `load` naming the values it reads. `to_collect?`, `refundable?`, `unpaid?`, `receipt_available?` and `payment_instruction` are examples.

Ash inlines an expression calculation into the SQL of every expression that references it, with no way to compute it once. The Balance expands the grand total five times on its own, so each boolean over it carried another copy. The admin order page's read reached 65 KB of SQL with 558 bind parameters and 67 copies of the grand total. The whole read spent about 20 ms in Postgres locally, but about 75 ms in Elixir building the query, and building it was most of the read's 470–615 ms in production. With the booleans computed from values loaded once, the read fell from 97 ms to 42 ms locally, and Postgres time didn't change.

## Considered Options

- **Keep every calculation an expression.** Rejected: the cost grows with each boolean added over the Balance, and every read of an order pays it.
- **Compute every derived calculation in Elixir.** Rejected: a calculation computed in Elixir can't be filtered, sorted or aggregated on, and the ones that are (`settled?`, `payable?`, `payment_status`, `payment_link_open?`, `holds_money?`) must stay in SQL.
- **One module per calculation** (`use Ash.Resource.Calculation`). Tried first, then inlined: two dozen files of one or two lines each kept each rule away from the expressions it derives from. A module is still right for logic too long to read inside the resource, like `AdminMenuActions`.
- **Store the grand total or Balance as a column.** Taken for a placed order's grand total (TASK-188, 2026-11-11), once the measures below left the admin order read at 225 ms in production, most of it Ash building the chain's SQL. Every input to the live grand total is already stored on the order or its lines, so the column is a cache that only a write path skipping the snapshot can put out of step. See the revision below.
- **Store amount paid, held and invoiced as columns.** Built and turned down (TASK-190, 2026-11-11). The grand total could be stored because nothing changes it once an order is placed, and storing it took 20–30% off several reads. These three change with every payment, invoice and credit note, so a stored copy has to be recomputed under a row lock on each write, and `Ash.load` no longer refreshes them: code that reloads after a write must remember to re-read the row or it reads stale money without an error. That bought 17% on the admin order read (five reads 88.7 → 74.0 ms on the production dump, aggregate queries built per read 258 → 131), about 25 ms in production, which Jennie wouldn't notice. The sums stay worked out from the `Payment` rows (ADR 0002).

## Revision (2026-11-11): a placed order's grand total is stored

- A placed order stores its grand total in a column, set in `Changes.SnapshotVatBreakdown` alongside `vat_breakdown`, and by `sell_gift_voucher`, which sets its breakdown directly. A migration backfills placed orders from the live grand total, and a check constraint requires the column on every placed order, so a write path that misses it fails instead of leaving a wrong Balance.
- An order's `total_due` reads the column. A cart has no stored total, so the checkout calculations in `Payable` (`voucher_amount`, `stripe_amount`) read a total each resource defines: the live `grand_total` on an order, `total_due` on a course booking. Not `stored || live`: Ash would still inline the live branch.
- Changing a placed order's lines, through any `LineItem` action, or its fees or promotion, through any `Order` update, refreshes the stored total and VAT breakdown (`LineItem.Changes.RefreshPlacedOrder`, `Order.Changes.RefreshWhenRepriced`), so a new action can't forget to. Only `Ash.Seed` and raw SQL get past it.
- A test asserts the stored total equals the live grand total after every write path that places or changes a placed order. Nothing checks it in production: only code that skips the snapshot can break it, and the tests cover that.
- Before an order is placed, `payment_status` reads `pending` and `Validations.Payable` checks `checkout_total`, since a cart has no Balance.
- Measured on the production dump of 2026-11-11 (laptop, medians of 30): five admin order reads 130 → 96 ms (153 → 136 KB of SQL), unsettled orders 9.7 → 4.3 ms, orders due soon 5.8 → 3.9 ms, the admin order list 13.2 → 10.5 ms.
- The calculations this ADR moved to Elixir were measured again with the stored total (TASK-189, the same dump, medians of 30, noise about ±3 ms on the admin order read). All of them as expressions left the Overview mount unchanged (18.5 ms) but took five admin order page mounts from 121 to 156 ms and 156 to 199 KB of SQL. One at a time:
  - Still measurably slower as expressions, so they stay in Elixir: `to_collect?`, `to_refund?`, `refundable?`, `unpaid?`, `receipt_available?`, `invoiceable?`, `payment_reminder_sendable?` (each 1–8 KB more SQL on the admin order read), `pass_it_on_card_removable?` (+14 ms there), `payment_emailable?` (its dependencies are in Elixir, so as an expression Ash evaluates it in memory, slowing the admin order read), the order's and the booking's `payment_overdue?` (+2 KB and 1–3 ms on the Overview), the order's `paid?` (+6 KB and 3–8 ms on four payment link reads) and both `payment_instruction`s (+1 KB and about 1 ms on the account page's lists).
  - No measurable difference, so expressions again: the booking's `cancelled_unsettled?` and `paid?` (a booking's Total due is cheap; the course page and a read of every booking took the same time).
  - The Invoice ones weren't measured: the stored total doesn't change their chain.

## Consequences

- A new calculation starts as an expression. It moves to Elixir only when it builds on the Balance chain, nothing queries it, and the read it's loaded in is measurably slower for it.
- Filtering, sorting or aggregating on one computed in Elixir raises an error. If one is ever needed in a query, turn it back into an expression and accept the cost.
- One that restates an expression it no longer references (`to_collect?` and `to_refund?` restate `settled?`; `unpaid?` restates `payable?`) says so in a comment, and changes with that expression.
- The rule stays in the resource, with its description, so the UI reads it as a calculation either way.
- An expression on the chain references each costly expression as few times as it can, since each reference is another copy in the SQL. `balance` is written with `GREATEST`/`LEAST` so it carries its due amount twice instead of five times, and `payment_status` checks `balance` once. The fragment can't be evaluated in Elixir, so loading `balance` on records in memory always queries. Together these took the admin order read from 41 ms to 31 ms on a production dump.
